Guidance — design rationale

What changed & why

  • The mockup labels itselfEverything inside the accent-framed panel tagged “QUEST APP UI” is the proposed app UI — the flow starts at step 1, “What are you connecting to?”. Everything outside the frame is guidance: the legend, the connection-type switcher, the per-type notes, and this section. None of the guidance ships.
  • Guided steps instead of one long scrollThe old form was a single ~2,000-line scrolling list. The redesign splits it into four steps — protocol, server, sign-in, review — one decision per screen, with targets sized for a headset pointer.
  • Protocol and auth mode are decided firstVNC's password-vs-account choice used to sit as radio buttons between the name and host fields. Now it's part of step 1, so every later screen only shows fields that apply.
  • Sign-ins are created in placePicking “+ New sign-in” used to eject you into Settings and lose your place. It now opens a sheet right over the form — save, and the new sign-in is already selected.
  • Credential forms match the credentialThe old form was the same name/user/password blob for everything. A VNC password now gets its 8-character counter, a username + password login explains it wants an account on the target machine, and key import is shaped for pasting a PEM.
  • SSH choices are explicit, not interdependentUsername (saved / type / ask), auth (password / key), and jump host are separate segmented choices, and picking a jump host draws the route: laptop → bastion → target. The username lives in exactly one place — typing a password by hand asks for the password only, and it pairs with whichever username mode is selected above.
  • A review screen before savingStep 4 summarises the whole connection up top with Edit links back to each step, then groups the extras — display & audio, tunnel, files, network — into cards instead of a flat toggle pile.
  • The vault knows what things areSign-ins and SSH keys are grouped separately, with kind and PIN badges and a “used by N connections” line, so it's obvious what breaks if you delete one.
  • Discovery only shows what you pickedAn SSH server can't be found by scanning the local network, so step 2 has no finder for SSH — just name, host and port, no explanation needed. Where the finder does appear, it only lists servers of the type you selected: RDP finds RDP PCs, VNC finds VNC servers, and switching protocol swaps the list.
  • VNC is a general protocol, not Mac-onlyVNC wording no longer assumes the target is a Mac — it runs on Windows, Linux and media boxes too. Mac Screen Sharing appears exactly once, as the example for username + password sign-in, and the password flow just says “VNC password”.
  • Editing looks like creating, prefilledThe New | Edit toggle at the top of the panel loads a saved connection with every step already filled in — protocol, server, sign-in, options — and the stepper stays fully visitable. The footer just switches to “Save changes” — there's no delete here, since removing a connection already lives on the main launcher.
  • Private keys are replace-only, never displayedEditing an SSH key shows an empty box, exactly like a password field: paste a new key to replace the saved one, or leave it blank to keep it. The saved key is never rendered anywhere — only the public key can be viewed or copied, which is safe to share.
  • Required fields block the flow, in redA blank connection name, host or port on step 2 — the port must also be a number from 1 to 65535 — or a missing sign-in where the protocol demands one (RDP, both VNC modes) — shows red error text under the field and dims Continue until it's fixed, validated live as you type. SSH is the exception: its credentials are genuinely optional, so its step 3 never blocks. The same rules gate “Save changes” in edit mode.
  • VNC file pairing lists plain connection namesThe File access card pairs a VNC connection with an existing SSH connection, and the dropdown shows just connection names — None, Mac mini, homelab — no protocol jargon or suffixes.
  • Mac logins save both names, onceA Mac account has a full name and a short name, and the two protocols want different ones: Screen Sharing signs in with the full name, SSH connects with the short name. A Mac login stores both in a single sign-in, so each connection resolves the right name automatically — no per-connection ambiguity. (Implementation note: this is the one approved data-model change: SavedCredential gains an optional shortName; VNC auth uses user, SSH uses shortName ?: user.)
  • Short names fill themselves in, macOS-styleMac login short names auto-fill from the full name with macOS's rules (lowercase, strip diacritics, drop spaces and disallowed characters) until you override them — same propose-and-replace behavior as macOS user creation. Type in the Short name field and the suggestion stops; clear it and it resumes. A short name with anything outside lowercase letters, numbers, _ - . gets the red error and blocks saving.
